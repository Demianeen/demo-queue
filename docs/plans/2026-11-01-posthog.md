# PostHog analytics, error tracking and LLM analytics

## Outcome

Demo Queue reports to PostHog on EU Cloud: what organisers, teams and judges
do, errors from the browser, the Next.js server and Convex actions, and every
OpenAI call with its tokens, cost and result. On an event night one dashboard
shows whether submissions, judging, AI summaries and the stage screen are
healthy, and alerts say when they are not. Nothing personal or secret leaves
the app: no emails, phone numbers, names of people, judge or status tokens,
README or code text, prompts, model replies or API keys.

This is a plan only. Nothing is installed and no PostHog or env var setting
is changed by this PR.

## What the app has today

- No analytics and no error reporting service. Server signals are
  `console.log` JSON in Convex (`ai-summary`, `ai-usage`) and
  `console.error` in the workspace layout.
- AI usage is already logged per call in the `aiUsage` table
  (`convex/aiUsage.ts`, `logAiUsage`) with model, tokens and a result
  (`saved`, `retried`, `rejected`, `discarded`, `failed`, `error`), and shown
  on the AI usage page.
- OpenAI calls, both through the Vercel AI SDK (`ai@6`, `generateText` with
  `Output.object`) in `"use node"` Convex actions:
  - `convex/aiSummaryAction.ts`, `generateSubmissionSummary`: a summary of a
    team's project for judges. The prompt holds the description, README,
    dependency files and code excerpts.
  - `convex/ai.ts`, `aiShuffle` and `aiShuffleMcp`: the lineup order. The
    prompt holds team names, demo titles, tracks and the organiser's
    instruction.
  - `convex/aiUsage.ts` makes no OpenAI call; it is the usage ledger.
- Two `TODO(posthog)` comments in `convex/aiSummaryAction.ts`: send the
  `ai-summary` log events (`log`) and the code-read input failures
  (`logInputFailure`) to PostHog with the same fields.
- Convex env vars are declared in `convex/convex.config.ts` (`defineApp`
  `env`); Next.js public env vars are validated in `app/env.ts`.
- Mutations already hand side effects to actions with
  `ctx.scheduler.runAfter(0, internal...)` (status link emails, judging sheet
  sync). Server-side capture can use the same pattern.
- `middleware.ts` matches only workspace paths and `/callback`, so a new
  `/ingest` proxy path is not caught by AuthKit.

## Privacy rules

Never sent, from any surface: emails, phone numbers, names of people, judge
tokens, status-link tokens, old admin tokens, OAuth codes and state, README or
code text, project descriptions, prompts, model replies, error messages from
the OpenAI API (they can quote the prompt), and API keys.

How:

1. **One URL scrubber**, `lib/analytics-url.ts`, with unit tests. It
   rewrites `/judge/[slug]/<token>`, `/s/[slug]/<token>` and
   `/admin/[slug]/<token>` to `.../[token]`, and drops every query parameter
   except `view`, `sort`, `status`, `track` and `utm_*`.
2. **posthog-js `before_send`** runs the scrubber on every property whose
   name contains `url` or `href` (as PostHog's own example does), including
   `$set` and `$set_once`, plus `$pathname`, `$referrer` and
   `$initial_referrer`, which that example misses. URL-based PostHog
   features read `window.location.href` directly, so PR 1 checks the
   `get_current_url` option the SDK types list for this.
3. **Replay URLs**: `session_recording.maskCapturedNetworkRequestFn` runs on
   the page URL in recordings as well as on network requests, so the same
   scrubber goes there. Replay stays off on token pages anyway.
4. **Autocapture masked** and limited to the workspace (`url_allowlist`);
   `maskAllInputs` stays on (the default).
5. **Server events are allowlisted**: one `capture` helper takes a known
   event name and a typed property object, so free text cannot be added by
   accident.
6. **Exceptions are redacted**: `before_send` passes `$exception` messages
   through a redactor that removes emails, phone numbers and anything shaped
   like a token. `ConvexError` messages can name people (for example
   "Redistribute these judges before removing them: ...").
7. **LLM events carry no content**: no `$ai_input`, no `$ai_output_choices`,
   no error message.
8. **No person profiles for anonymous visitors**: `identified_only` is the
   posthog-js default, and anonymous server events set
   `$process_person_profile: false`.
9. Project setting: IP capture stays off (the default for new EU projects).

## Consent (UK and EU attendees)

Teams and judges arrive from a link at an event and never see a settings
page, so a cookie banner there would mostly be clicked away. PostHog's
cookieless mode stores nothing on the device and counts visitors with a
daily salted hash of IP, user agent and host on its servers. Its docs say to
avoid `identify` in that mode, and it turns off session replay and surveys.

**Agreed: cookieless everywhere, organiser identity on the server.**

- posthog-js runs with `cookieless_mode: 'always'` on every page. No banner.
- Browser events carry `organization_id` as a plain event property
  (`posthog.register`), not a person. The WorkOS organisation id is not
  personal data.
- Organiser identity lives on server-side events from Convex, where the
  `distinct_id` is the WorkOS user id and `$groups.organization` is set.
  Nothing is stored on the organiser's device for this.
- No session replay and no surveys.
- Remaining legal step: one line in a privacy notice ("we measure usage
  without cookies"); the wording is Demian's call.

**Later, if replay is wanted: a banner in the workspace only.** `cookieless_mode:
'on_reject'` on workspace pages: nothing is captured until the organiser
chooses; on accept posthog-js uses a cookie, `identify` and `group` run, and
session replay works; on reject it falls back to cookieless counting. Public
pages stay `'always'`. More to build (banner, `reset` on sign out) for
replay of a small number of organisers.

## Identity and groups

- **Organisers, server side**: `distinct_id` is the Convex identity
  `subject` (the WorkOS user id), never `tokenIdentifier`, and
  `$groups: { organization: <WorkOS organisation id> }`. No person
  properties: no email, no name.
- **Organisation group properties**: `name` only, sent once with a
  `$groupidentify` event when an organisation is first seen or renamed.
- **Teams, judges, stage**: never identified. Events carry the event id,
  slug, type and phase, never a judge key, token or contact.
- **Background work** (AI summaries, emails, sheet sync): `distinct_id`
  `system`, `$process_person_profile: false`, and the organisation as a plain
  property, since PostHog applies `$groups` only to identified events.
- **Group analytics** is a paid add-on and, once on, bills every identified
  event in the project (first 1M a month free). Without it, the organisation
  id is still an event property to filter and break down by.
- Only if the workspace banner is added later: `identify`, `group` in a small client
  component inside `EventsWorkspace` (which gets `userId` from the layout
  next to `email` and `displayName`), and `posthog.reset()` before the
  `logOut` form in `components/WorkspaceAccountMenu.tsx` submits.

## LLM analytics

**Proposed: our own `$ai_generation` events from `logAiUsage`.** Both
features already call it for every OpenAI call, retries and failures
included, with the model, token counts and our result code. PostHog's
manual capture accepts `$ai_generation` through the plain capture API, so
no new dependency is needed.

Properties: `$ai_trace_id` (one per summary run or shuffle), `$ai_span_name`
(`summary` or `shuffle`), `$ai_provider` (`openai`), `$ai_model`,
`$ai_input_tokens`, `$ai_output_tokens`, `$ai_latency` (seconds),
`$ai_http_status`, `$ai_is_error`, plus `feature`, `result`, `event_id`,
`practice` and `organization_id`. No `$ai_input`, no `$ai_output_choices`,
no `$ai_error` text. PostHog prices the call from the model and tokens; our
own estimate stays on the AI usage page.

Alternative: `@posthog/ai` `withTracing` around the AI SDK model. It
supports AI SDK v5 and v6 (this repo is on v6) and rejects v7, where PostHog
moves to an OpenTelemetry span processor. It needs `posthog-node` in both
actions, `privacyMode: true` on the client to keep content out, and it
cannot see our result codes. The manual events survive an AI SDK upgrade
unchanged.

## MCP Analytics

Every organiser MCP tool call sends one `$mcp_tool_call` event in the shape
PostHog's MCP Analytics dashboards read
(https://posthog.com/docs/mcp-analytics/installation/other-languages). All
admin tools are built by `defineAdminTool` in `convex/mcpTools.ts`, and the
organisation and style tools by `convex/mcpWorkos.ts`, so the capture sits in
those two places, after the handler returns or throws.

| Property | Value |
| --- | --- |
| `$mcp_source` | `posthog_mcp_analytics` (required, or the dashboards ignore the event) |
| `$mcp_server_name` | `demo-queue` |
| `$mcp_tool_name` | the tool name |
| `$mcp_is_error`, `$mcp_duration_ms` | from the call |
| `$mcp_error_type` | a short code (`unauthorized`, `validation`, `not_found`, `operation_failed`); `$mcp_error_message` only when it is one of the fixed admin messages in `convex/mcpRuntime.ts`, redacted |
| `$session_id` | the MCP session id |
| `$mcp_client_name`, `$mcp_client_version` | from the client's `initialize` handshake |
| `distinct_id` | the WorkOS user id from the MCP token, with `$groups.organization` |
| `timestamp` | when the call started |

Never sent: `$mcp_parameters` and `$mcp_response`. Tool arguments and
results hold team names, contact details, judge names and scores.

### Agent intent (Proposed)

What it is for: each tool gets an extra `context` argument, and the agent
says in a sentence why it is calling the tool ("checking which judges still
have unscored projects before closing judging"). PostHog groups these into
intent clusters, so we learn what organisers ask their assistant to do with
Demo Queue, which jobs need three or four tool calls that one tool could do,
and where tool descriptions mislead agents. Tool names and counts alone
cannot show that.

The risk is that it is free text written by an agent that has just read
team names and emails. Done right:

- `context` is an optional string, at most 300 characters, added once in
  `defineAdminTool` and `convex/mcpWorkos.ts` (the schemas set
  `additionalProperties: false`, so it must be listed). Its description
  follows PostHog's recommended wording: say why you are calling the tool,
  in general terms, refer to people by role, and leave out names, emails and
  other personal details.
- It is removed from the arguments before validation and the handler, so no
  tool behaves differently.
- Before sending, the shared redactor replaces emails, phone numbers, URLs,
  tokens and key-like values with `[redacted]`, as PostHog's guide lists,
  then cuts to 300 characters. It is sent as `$mcp_intent` with
  `$mcp_intent_source: "context_parameter"`; nothing is sent when it is
  blank.
- Names of people cannot be caught by a pattern, so the description and the
  redactor are the guard, not a guarantee. A test checks the redactor;
  after a week of real use, read the intent clusters once and drop the
  feature if names show up.

## Alerts

Insight alerts check hourly or daily on the free plan (every 15 minutes
needs the Boost package) and a free organisation gets 5. They notify by
email, Slack, Discord, Teams or webhook. Error tracking alerts ("issue
created or reopened", "spike") go to Slack, Discord, Teams or a webhook,
not email.

| Alert | Rule (Proposed) | Why |
| --- | --- | --- |
| AI summaries failing | `ai_summary` with `status = failed`, at least 3 in an hour | Judges see no summary |
| GitHub rate limited | `reason` is `code_rate_limited` or `readme_rate_limited`, at least 5 in an hour | `GITHUB_TOKEN` is missing or spent |
| Summary budget hit | any `ai_summary` with `reason = daily_budget` in an hour | The daily cap was hit during an event |
| Submissions failing | `submission_failed`, more than 5 in an hour | Teams cannot submit |
| Error spike | `$exception`, more than 20 in an hour | A page is failing for many people |
| New error issue | error tracking, issue created or reopened | Something broke (Slack or webhook only) |
